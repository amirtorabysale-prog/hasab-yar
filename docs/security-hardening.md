# امنیت و پایداری داده — مرحلهٔ ۳ و پس از آن

حساب‌یار اطلاعات مالی خصوصی نگه می‌دارد. کنترل‌های پایهٔ نشست در مرحلهٔ ۳، جداسازی دفتر و نقش‌ها در مرحلهٔ ۴ و پشتیبان رمزگذاری‌شده در مرحلهٔ ۵ اضافه شده‌اند.

## کنترل‌های اجراشده

- نشست با توکن تصادفی نگه‌داری می‌شود و فقط هش توکن در SQLite قرار می‌گیرد.
- کوکی نشست `HttpOnly`، `SameSite=Strict` و در محیط Production دارای `Secure` است.
- هر کاربر حداکثر پنج نشست فعال دارد.
- تمام درخواست‌های تغییردهنده علاوه بر بررسی مبدأ، به توکن CSRF متصل به همان نشست نیاز دارند.
- تلاش‌های ناموفق ورود در دیتابیس و با اثرانگشت هش‌شده ثبت می‌شوند؛ بعد از هشت خطا، ورود پانزده دقیقه قفل می‌شود.
- کاربر می‌تواند رمز مالک را تغییر دهد؛ پس از تغییر، همهٔ نشست‌های قبلی باطل می‌شوند.
- سیاست رمز: حداقل ۱۴ نویسه، دارای حرف و عدد، متفاوت از رمز قبلی و بدون نام کاربری.
- CSP، جلوگیری از نمایش در iframe، HSTS در Production، جلوگیری از MIME sniffing و محدودیت دسترسی دوربین/مکان فعال است.
- پاسخ‌های API مالی با `no-store` ارسال می‌شوند و Service Worker آن‌ها را Cache نمی‌کند.

## متغیرهای Railway

سه مقدار زیر باید در Variables سرویس تعریف شوند. هر Secret بهتر است حداقل ۳۲ بایت تصادفی باشد و هرگز داخل Git قرار نگیرد.

```env
CSRF_SECRET=...
AUTH_FINGERPRINT_SECRET=...
TRUST_PROXY_HOPS=1
```

`ADMIN_PASSWORD` نباید مقدار نمونهٔ فایل `.env.example` باشد. اگر کاربر مالک قبلاً در دیتابیس ساخته شده باشد، تغییر متغیر محیطی رمز او را عوض نمی‌کند؛ از بخش «تغییر رمز مالک» داخل برنامه استفاده کنید.

## کنترل‌های تکمیلی

- هر دفتر پایگاه‌دادهٔ مالی مستقل دارد و دسترسی از روی عضویت و نقش بررسی می‌شود.
- پشتیبان قابل حمل با AES-256-GCM و کلید مشتق‌شده با scrypt رمزگذاری می‌شود.
- پیش از بازیابی، فایل کامل اعتبارسنجی و یک پشتیبان نقطهٔ بازگشت ساخته می‌شود؛ بازیابی داخل تراکنش دیتابیس انجام می‌شود.
- بعد از بازیابی، نشست سایر اعضای همان دفتر باطل می‌شود تا دادهٔ بازگشته با نشست‌های قدیمی تغییر نکند.
