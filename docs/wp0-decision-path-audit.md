# ممیزی مسیر تصمیم — گام ۲ از WP-0

وضعیت: کامل‌شده، پیش از هر تغییر کد
پایهٔ آزمون در لحظهٔ ممیزی: ۹۸۲ تست، همه سبز (`npm test`)

این سند به یک سؤال جواب می‌دهد: **امروز، از لحظه‌ای که کاربر حرف می‌زند تا لحظه‌ای که سند در دفتر می‌نشیند، تصمیم حسابداری کجاها گرفته می‌شود؟** هدف، پیدا کردن جاهایی است که تصمیم گرفته می‌شود ولی کسی آن را «تصمیم» صدا نمی‌زند.

## ده جایی که امروز تصمیم حسابداری ضمنی گرفته می‌شود

ترتیب بر اساس شدت اثر است، نه ترتیب اجرا.

### ۱. `server/transactionEvent.js:17` — جدول دوسطری‌ای که «پرداخت یعنی هزینه» را قفل کرده

```js
const KIND_BY_TYPE = Object.freeze({
  income: EVENT_KINDS.CASH_INCOME,
  expense: EVENT_KINDS.CASH_EXPENSE,
});
```

این کوچک‌ترین و پرمصرف‌ترین تصمیم حسابداری کل سیستم است. هر خروج وجهی که از مسیر عادی بیاید، بدون هیچ سؤالی «هزینهٔ دوره» می‌شود. پیش‌پرداخت، ودیعه، خرید موجودی، خرید دارایی، و پرداخت بدهی همگی از همین دو سطر رد می‌شوند. هیچ‌جا نوشته نشده «فرض کردیم این هزینه است»؛ فقط هست.

### ۲. `shared/accountingRules.js:68` — treatment به kind جوش خورده

```js
case EVENT_KINDS.CASH_EXPENSE:
  return plan(event.kind, { role: ROLES.EXPENSE_CATEGORY, ... }, { role: ROLES.CASH, ... }, ...);
```

حتی اگر بالادست بفهمد این پرداخت یک پیش‌پرداخت است، جایی برای گفتنش وجود ندارد. `kind` هم‌زمان می‌گوید «چه اتفاقی افتاد» و «چه سندی بخورد». این همان شکاف ۵ ممیزی خط مبنا است و اینجا خطش پیدا شد.

### ۳. `server/gemini.js:16` — قرارداد AI یک تصمیم را به‌عنوان واقعیت می‌خواهد

```js
required: ['amount', 'type', 'category', 'confidence'],
type: { type: 'STRING', enum: ['income', 'expense'] },
```

schema فعلی درست کار می‌کند که نام و کد حساب و بدهکار/بستانکار نمی‌خواهد. ولی `type` یک واقعیت نیست؛ یک طبقه‌بندی حسابداری است. با پرسیدنش از مدل، اولین و مهم‌ترین انشعاب ماهیت به مدل زبانی سپرده شده. `category` هم عملاً حساب هزینه را تعیین می‌کند، چون در بند ۱۰ به ساخت حساب می‌رسد.

### ۴. `server/transactionEvent.js:84` — تنها راه فرار از بند ۱، مشروط و خاموش است

```js
function settlementDirectionFor(item, counterpartyBalance) {
  if (!item.contactId || !Number.isFinite(Number(counterpartyBalance))) return null;
  ...
}
```

این تابع نطفهٔ نگهبان «اول تسویه» است و منطقش درست است. ولی دو شرط دارد: طرف حساب باید شناسایی شده باشد، و ماندهٔ او باید معلوم باشد. اگر هرکدام نباشد، `null` برمی‌گردد و رویداد بی‌صدا به بند ۱ می‌افتد. یعنی «بررسی تسویه انجام نشد» و «تسویه‌ای در کار نبود» امروز از هم قابل تفکیک نیستند.

### ۵. `shared/financialEvent.js:79` — واقعیت‌های لازم اصلاً قابل بیان نیستند

رویداد این فیلدها را دارد: `kind, amount, occurredAt, dueAt, category, counterparty, counterpartyId, accountId, reference, settlementDirection, description, source, evidence`.

هیچ‌کدام از این‌ها وجود ندارند: دورهٔ مصرف، تاریخ شروع پوشش، قابل‌استرداد بودن، هدف از خرید، عمر مفید، تاریخ آماده‌به‌کاری، مرجع قرارداد، تفکیک مالیات.

نتیجه‌اش این نیست که این واقعیت‌ها گم می‌شوند؛ این است که **نبودشان قابل گزارش نیست**. موتور نمی‌تواند بگوید «دورهٔ پوشش را نمی‌دانم»، چون جایی برای ندانستنش ندارد. `dueAt` هم برای هر نوعی که در `DATED_FORWARD` نباشد بی‌صدا دور ریخته می‌شود.

### ۶. `shared/confidenceEngine.js:117` — دروازه، کفایت حسابداری را نمی‌سنجد

`routeEvent` سه چیز را نگاه می‌کند: blockerهای بالادستی، سیاست دفتر، و نمرهٔ عددی مؤلفه‌ها. هیچ‌کدام نمی‌پرسند «آیا واقعیت‌های لازمِ ماهیت این رویداد موجود است؟»

یک پیش‌پرداخت بیمه با مبلغ روشن، تاریخ روشن، بانک روشن و دستهٔ انتخاب‌شده، نمرهٔ نزدیک به ۱ می‌گیرد و مسیر `auto` را رد می‌کند — در حالی که دورهٔ پوششش معلوم نیست و سندش غلط است. این دقیقاً شکاف ۳ ممیزی خط مبنا است: اطمینان بالا، ماهیت مبهم.

### ۷. `server/transactionEvent.js:52` — «کامل بودن» با معیار رابط کاربری سنجیده می‌شود

```js
put(CONFIDENCE_COMPONENTS.COMPLETENESS, supplied.category ?? certain(Boolean(item.category), 'دسته انتخاب شده است.'));
```

مؤلفهٔ «کامل‌بودن اطلاعات» یعنی «آیا دسته انتخاب شده؟». این یک واقعیت رابط کاربری است، نه یک واقعیت حسابداری. انتخاب شدن دسته هیچ چیزی دربارهٔ کافی بودن اطلاعات برای ساخت سند درست نمی‌گوید.

### ۸. `server/financialEventStore.js:121` و `:195` — نقشه دو بار و با دو کد متفاوت ساخته می‌شود

در لحظهٔ ثبت، `planJournal(event)` اجرا و نتیجه‌اش در ردپای `captured` ذخیره می‌شود. در لحظهٔ تأیید، **دوباره** `planJournal(event)` با کد آن روز اجرا می‌شود. رویدادی که دو هفته در صف مانده و در این فاصله قاعده‌ای عوض شده، سندی می‌خورد که با آنچه به حسابدار نشان داده شده بود فرق دارد و هیچ هشداری هم نمی‌دهد. شکاف ۴ ممیزی خط مبنا، با شمارهٔ خط.

### ۹. `shared/accountingRules.js:139` — «آیا سود را تکان می‌دهد» استنتاج می‌شود، نه اعلام

```js
export function affectsProfit(kind) {
  const plan_ = { kind, amount: 1, category: 'x', ... };
  return planJournal(plan_).lines.some(...);
}
```

یک رویداد ساختگی می‌سازد تا از روی سندش بفهمد اثر سود و زیانی دارد یا نه. امروز جواب درست می‌دهد، ولی یعنی این خاصیت جایی اعلام نشده و هر خانوادهٔ جدیدی که treatment متغیر داشته باشد، اینجا جواب بی‌معنا می‌گیرد.

### ۱۰. `server/roleResolver.js:46` — حساب دفتر کل از روی نام دسته متولد می‌شود

```js
database.prepare('INSERT INTO ledger_accounts (id,code,name,type,normal_side,source_kind,source_key) VALUES (?,?,?,?,?,?,?)')
```

نقش و کلید که به حساب واقعی نگاشت می‌شوند، اگر حسابی نباشد ساخته می‌شود. یعنی یک دستهٔ اشتباه یا یک تایپ در نام، بی‌صدا یک حساب تازه در دفتر کل می‌سازد. این با خودش بد نیست — کدینگ هر دفتر فرق می‌کند — ولی وقتی با بند ۳ جمع شود، مسیری می‌شود از برداشت مدل زبانی تا ساخت حساب، بدون هیچ ایستگاه تصمیم.

## جمع‌بندی: زنجیرهٔ کامل یک خطای خاموش

```
«حق بیمه یک‌ساله رو از بانک ملت دادم»
  → AI می‌گوید type=expense                         (بند ۳)
  → KIND_BY_TYPE می‌گوید cash-expense               (بند ۱)
  → رویداد جایی برای «دورهٔ پوشش» ندارد             (بند ۵)
  → COMPLETENESS می‌گوید کامل است، چون دسته دارد     (بند ۷)
  → routeEvent نمرهٔ بالا می‌دهد و ماهیت را نمی‌پرسد  (بند ۶)
  → planJournal هزینهٔ دوره می‌زند                   (بند ۲)
  → roleResolver حساب «بیمه» را می‌سازد             (بند ۱۰)
  → سند ثبت می‌شود. هیچ‌کس چیزی نپرسید.
```

هر هفت ایستگاه درست کار کردند. هیچ باگی وجود ندارد. سند غلط است.

## آنچه امروز درست است و نباید دست بخورد

- جدایی زبان از حسابداری در `shared/financialEvent.js` — همان مرزی است که WP-0 رویش می‌سازد؛
- قاعده به‌صورت تابع خالص و بر پایهٔ نقش، نه کد حساب؛
- کنترل توازن داخل خود `plan()`، پیش از رسیدن به لایهٔ ثبت؛
- یکتایی با `source_event_id` در سطح دیتابیس، نه در لایهٔ بالادست؛
- ردپای کامل: captured، posted، approved، reversed، rejected، handed-over؛
- معکوس‌سازی به‌جای حذف، با کنترل صریح «سند پیدا نشد → برگشت انجام نشد»؛
- صف جدا برای کاربر و حسابدار؛
- `neverAutomatic` و `allowAiOnlyAutoPost: false` در سیاست پیش‌فرض؛
- لنگر سند (`journal_source`) که از ثبت دوم هنگام مهاجرت جلوگیری می‌کند.

## نتیجه برای WP-0

پنج بند از ده بند بالا (۱، ۲، ۳، ۵، ۶) دقیقاً همان چیزی هستند که `AccountingDecision` و `FactRequirement registry` قرار است حل کنند. بند ۸ با `PostingPlan` تغییرناپذیر حل می‌شود. بند ۴ به WP-1 می‌رود. بندهای ۷، ۹ و ۱۰ کوچک‌اند و در همین فاز اصلاح می‌شوند.

هیچ‌کدام نیاز به بازنویسی ندارند. مسیر، جای خالیِ یک ایستگاه را دارد: بین `normalizeFinancialEvent` و `planJournal`.
