# طرح پیاده‌سازی WP-0 — ستون فقرات تصمیم

وضعیت: در انتظار بازبینی مالک محصول
پیش‌نیازها: ممیزی مسیر تصمیم (کامل)، چهار تصمیم پایه (تصویب‌شده)

## ایدهٔ مرکزی، در یک جمله

مسیر امروز یک ایستگاه کم دارد. بین `normalizeFinancialEvent` که می‌گوید «چه اتفاقی افتاد» و `planJournal` که می‌گوید «سند چه باشد»، هیچ چیزی نمی‌گوید «این از نظر اقتصادی چیست و برای تصمیم گرفتن چه چیزی لازم دارم». همهٔ این فاز، ساختن همان ایستگاه است.

```
امروز:   رویداد ──────────────────────────────────→ planJournal
فردا:    رویداد ──→ خانواده ──→ واقعیت‌های لازم ──→ تصمیم ──→ planJournal
                                      │
                                      └──→ سؤال، یا صف حسابدار
```

## فایل‌های تازه

| فایل | مسئولیت | وابستگی |
|---|---|---|
| `shared/economicFamily.js` | ۱۲ خانواده + طبقه‌بند؛ `unknown` یک پاسخ معتبر است | ندارد |
| `shared/factRequirements.js` | هر خانواده واقعیت‌های لازمش را اعلام می‌کند؛ تولید `missingFacts` و یک سؤال فارسی | economicFamily |
| `shared/accountingDecision.js` | موجودیت تصمیم + پنج وضعیت + تابع خالص `decide()` | هر دو بالا |
| `shared/aiFactContract.js` | schema سخت‌گیر استخراج؛ حساب و بدهکار/بستانکار ممنوع | ندارد |
| `shared/recognitionSchedule.js` | برنامهٔ ماهانهٔ خط مستقیم، idempotent، با ته‌ماندهٔ گرد کردن روی قلم آخر | ندارد |

همه تابع خالص، بدون دیتابیس و بدون شبکه — مثل بقیهٔ `shared/`.

## تغییر در فایل‌های موجود

| فایل | تغییر | ریسک |
|---|---|---|
| `shared/financialEvent.js` | افزودن فیلدهای واقعیت: `servicePeriodStart`, `servicePeriodEnd`, `refundable`, `intendedUse`, `contractReference`. همه اختیاری و افزایشی | کم — رویداد قدیمی بدون این فیلدها معتبر می‌ماند |
| `shared/automationPolicy.js` | افزودن فلگ `engineV2`، پیش‌فرض `false` | کم |
| `shared/confidenceEngine.js` | `routeEvent` تصمیم را هم می‌گیرد؛ `needs-user-input` و `blocked` بالاتر از هر نمرهٔ عددی می‌نشینند | متوسط — قلب مسیریابی |
| `server/financialEventStore.js` | ذخیرهٔ تصمیم؛ **نقشهٔ ذخیره‌شده در تأیید دوباره ساخته نمی‌شود** | متوسط — رفع بند ۸ ممیزی |
| `server/transactionEvent.js` | وقتی `engineV2` روشن است، `KIND_BY_TYPE` از مسیر خارج می‌شود و جایش تصمیم می‌نشیند | بالا — پرترافیک‌ترین مسیر |

## دیتابیس

یک جدول تازه و یک ستون:

```sql
CREATE TABLE accounting_decisions (
  id TEXT PRIMARY KEY,
  event_id TEXT REFERENCES financial_events(id),
  family TEXT NOT NULL,
  treatment TEXT,
  policy_key TEXT NOT NULL,
  policy_version TEXT NOT NULL,
  recognition_date TEXT,
  recognition_method TEXT,
  required_facts TEXT NOT NULL DEFAULT '[]',
  missing_facts TEXT NOT NULL DEFAULT '[]',
  assumptions TEXT NOT NULL DEFAULT '[]',
  risk_level TEXT NOT NULL,
  explanation TEXT,
  source_references TEXT NOT NULL DEFAULT '[]',
  decision_status TEXT NOT NULL,
  posting_plan TEXT,          -- نقشهٔ قفل‌شده؛ در تأیید دوباره محاسبه نمی‌شود
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
ALTER TABLE financial_events ADD COLUMN decision_id TEXT;
```

مهاجرت افزایشی و برگشت‌پذیر است. رویداد قدیمی `decision_id` ندارد و همان‌طور که بود خوانده و نمایش داده می‌شود. هیچ دادهٔ تاریخی بازطبقه‌بندی نمی‌شود.

## ترتیب پنج‌روزه

**روز ۱ — قرارداد و تست‌های شکست‌خورده.** ۱۲ خانواده، رجیستری واقعیت‌ها، schema استخراج، و سه سناریوی دمو به‌صورت تست قرمز. هیچ پیاده‌سازی‌ای نوشته نمی‌شود.

**روز ۲ — توابع خالص.** طبقه‌بند، `decide()`، و برنامهٔ شناسایی ماهانه. تا پایان این روز تست‌های واحد سبز می‌شوند بدون اینکه دیتابیس دست بخورد.

**روز ۳ — دیتابیس و اتصال.** جدول تصمیم، قفل شدن نقشه، و عبور دادن مسیر `transactionEvent` از ایستگاه تازه پشت فلگ.

**روز ۴ — سؤال از راه صدا.** سخت‌ترین بخش؛ جزئیاتش پایین.

**روز ۵ — پیکرهٔ طلایی و regression.** رساندن پیکره از ۳۰ نمونهٔ فعلی به ۳۰ نمونهٔ پوشش‌دهندهٔ سه دستهٔ خواسته‌شده (۱۰ روشن، ۱۰ مبهم، ۱۰ ناقص)، اجرای کل ۹۸۲ تست، و اثبات اینکه با فلگ خاموش رفتار عوض نشده.

## سؤال از راه صدا — پرریسک‌ترین بخش

این تنها جایی است که هنوز طراحی قطعی ندارم و پیش از کد باید کد موجود را دقیق‌تر بخوانم.

آنچه می‌دانم: `shared/correction.js` جملهٔ اصلاحی را می‌شناسد و `previewCorrection` دارد، و رویداد منتظر در `financial_events` با وضعیت `pending` زنده می‌ماند. آنچه هنوز نمی‌دانم: چطور یک جواب کوتاه («از اول مهر») به یک رویداد منتظر بچسبد بدون اینکه کاربر کل جمله را تکرار کند، و چطور معلوم شود جواب مال کدام سؤال است وقتی دو مورد در صف باشد.

**رویکرد پیشنهادی:** آخرین سؤالِ پرسیده‌شده در همان نشست، مرجع ضمنی جواب کوتاه بعدی باشد — مثل مکالمهٔ آدم‌ها. اگر بیش از یک سؤال باز باشد، سیستم قبل از پذیرفتن جواب کوتاه، نام مورد را می‌گوید. اگر جواب مبهم بماند، هیچ چیز ثبت نمی‌شود.

این بخش را بعد از خواندن مسیر صدا دقیق‌تر طراحی می‌کنم و اگر از یک روز بیشتر شد، خبر می‌دهم.

## آنچه در این بسته ساخته *نمی‌شود*

- هیچ خانوادهٔ دیگری جز پیش‌پرداخت بیمه سیم‌کشی نمی‌شود؛
- نگهبان‌ها، کارت طرف‌حساب و تفکیک VAT مال WP-1 هستند؛
- نسخه‌دار شدن قواعد مال WP-2 است — اینجا فقط فیلدش ذخیره می‌شود؛
- هیچ ثبت خودکار تازه‌ای فعال نمی‌شود.

## شرط پذیرش

- سه سناریوی دمو از سر تا ته: دورهٔ مشخص → سند؛ دورهٔ نامشخص → سؤال؛ دورهٔ گذشته → هزینهٔ مستقیم؛
- سؤال از مسیر صدا پرسیده و جواب داده شود، و رویداد منتظر reload را رد کند؛
- افزودن خانوادهٔ جدید نیازی به تغییر هستهٔ طبقه‌بند نداشته باشد؛
- اجرای دوبارهٔ برنامهٔ شناسایی برای یک ماه، سند دوم نسازد؛
- **با فلگ خاموش، هر ۹۸۲ تست فعلی سبز بماند و رفتار بیت‌به‌بیت یکسان باشد.**
