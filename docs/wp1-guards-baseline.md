# ممیزی نگهبان‌ها — گام ۱ از WP-1

وضعیت: کامل‌شده، پیش از هر تغییر کد
پایهٔ آزمون: ۱۰۵۳ تست، همه سبز

پرامپت WP-1 می‌گوید این بسته عمدتاً کد موجود را **سخت** می‌کند، نه اینکه از صفر بسازد. پس اولین کار خواندن آن کد و گفتن این است که هر ماژول امروز چه چیزی را واقعاً پوشش می‌دهد.

## تصحیح ممیزی قبلی

در جدول «آنچه از قبل در کد هست» در طرح پروژهٔ نسخهٔ ۲ نوشته بودم `server/accountingTransfer.js` پایهٔ نگهبان انتقال داخلی است. **این غلط است.** آن فایل دربارهٔ ساخت فایل انتقال به نرم‌افزار حسابداری (پارسیان و CSV) است و هیچ ربطی به جابه‌جایی وجه بین حساب‌های خود واحد ندارد.

انتقال داخلیِ واقعی در `server/accounting.js:622` است: `postAccountTransferJournal`. اشتباه من از روی شباهت نام بود و باعث شده بود تخمین کار این فاز خوش‌بینانه باشد.

## آنچه هر ماژول واقعاً پوشش می‌دهد

### انتقال داخلی — `server/accounting.js:622`

قاعده‌اش **درست است**: سند دوطرفه بین دو حساب عملیاتی، بدون لمس هیچ حساب درآمد یا هزینه. مبدأ و مقصد یکسان رد می‌شود.

ولی یک مشکل جدی دارد که تا امروز ندیده بودمش:

```
expense / سایر هزینه‌ها  |  «از ملت به پاسارگاد ۵۰ میلیون منتقل کردم»
expense / سایر هزینه‌ها  |  «۵۰ میلیون از بانک ملت به صندوق آوردم»
```

یعنی انتقال داخلی که با **صدا** گفته شود، هزینه ثبت می‌شود. تابع `mentionsMultipleBanks` در `shared/banks.js:126` دقیقاً برای همین نوشته شده، تست هم دارد — ولی **هیچ کدی در برنامه صدایش نمی‌زند**. کد مرده است.

اثرش: هر جابه‌جایی پول بین دو حساب خودِ دفتر، یک زیان جعلی می‌سازد. این از خطای پیش‌پرداخت بدتر است، چون پیش‌پرداخت بالاخره هزینه می‌شود و این هیچ‌وقت.

### تسویه — `server/transactionEvent.js:84`

نطفهٔ نگهبان «اول تسویه» هست و منطقش درست است، ولی دو شرط دارد:

```js
if (!item.contactId || !Number.isFinite(Number(counterpartyBalance))) return null;
```

اگر طرف حساب شناسایی نشده باشد یا ماندهٔ او معلوم نباشد، `null` برمی‌گردد و رویداد بی‌صدا هزینهٔ تازه می‌شود. یعنی «بررسی تسویه انجام نشد» و «چیزی برای تسویه نبود» امروز از هم قابل تفکیک نیستند — و پرامپت صریح می‌گوید این دو باید جدا ثبت شوند.

### کارت طرف حساب — `server/db/counterpartyCard.js`

طراحی‌اش خوب است: از دفتر کل می‌خواند نه از جمع‌زدن جدول‌ها، پس شمارش دوباره ندارد. حتی اختلاف میان ماندهٔ دفتر و ماندهٔ اسناد باز را عمداً نشان می‌دهد به‌جای پنهان کردنش.

ولی **یک view است، نه یک نگهبان**. هیچ‌جا اجباری نیست که رویدادِ دارای طرف حساب به یک کارت resolve شود. صدا زدنش اختیاری است.

### چک — `server/db/cheques.js`

چرخهٔ عمر **درست است** و بهتر از آنچه فکر می‌کردم: `against` تعیین می‌کند چک بابت فروش تازه است (`income`) یا بابت طلب موجود (`receivable`)، وصول فقط اسناد دریافتنی را به نقد می‌برد، و برگشت، مبلغ را به حساب دریافتنی همان شخص برمی‌گرداند. یک چک، یک بار درآمد.

ولی یک خطر دارد: **پیش‌فرض `against` برابر `income` است.** چکی که بابت فاکتور قبلاً ثبت‌شده گرفته شده، اگر بدون تعیین صریح ثبت شود، درآمد را دو بار می‌شمارد. پیش‌فرض باید امن باشد، نه راحت.

### یکتایی — `server/financialEventStore.js`

`source_event_id` در سطح دیتابیس یکتاست و کار می‌کند. ولی **تک‌کاناله** است: همان فاکتور اگر یک بار با صدا و یک بار با عکس ثبت شود، دو `source_event_id` متفاوت دارد و دو سند می‌سازد. اثر انگشت محتوا وجود ندارد.

### ارزش افزوده

هیچ‌جا تفکیک نمی‌شود. نه در پارسر، نه در رویداد، نه در قاعده.

## جمع‌بندی وضعیت

| نگهبان | امروز | کار لازم |
|---|---|---|
| انتقال داخلی | قاعده درست، ولی از صدا غیرقابل‌دسترس | وصل کردن تشخیص به مسیر، نه نوشتن قاعده |
| اول تسویه | مشروط و خاموش‌شونده | اجباری کردن + ثبت «بررسی شد» |
| کارت طرف حساب | view خوب | تبدیل به پیش‌شرط resolve |
| چک | چرخه درست | عوض کردن پیش‌فرض ناامن |
| یکتایی | تک‌کاناله | اثر انگشت محتوا + operation id |
| تفکیک VAT | وجود ندارد | ساخت از صفر |

سه تا از شش مورد «وصل کردن» است، دو تا «سخت کردن»، و فقط یکی «ساختن». تخمین یک‌هفته‌ای که در طرح نوشته بودم با این تصویر می‌خواند — به شرطی که انتقال داخلی زودتر از بقیه برود، چون خطایش از همه پرهزینه‌تر است.

## قرارداد پیشنهادی نگهبان

```js
/**
 * هر نگهبان یک تابع خالص است با همین شکل.
 *
 * چرا یک شکل واحد: نگهبان‌ها باید روی هر تلاش ثبت اجرا شوند، بدون استثنا برای
 * هیچ خانواده‌ای. وقتی همه یک امضا دارند، اجرای همه‌شان یک حلقه است و
 * جاانداختن یکی‌شان ممکن نیست.
 */
guard(event, facts, context) => {
  name: string,              // شناسهٔ نگهبان، برای ردپا
  verdict: 'pass' | 'block' | 'rewrite',
  reason: string,            // به زبان حسابدار، نه نام فنی
  rewrite?: { ... },         // فقط برای verdict: 'rewrite'
  checked: true,             // همیشه ثبت می‌شود، حتی وقتی چیزی پیدا نشد
}
```

سه نکته که در این شکل عمدی‌اند:

**۱. `checked` همیشه ثبت می‌شود.** «نگهبان اجرا شد و چیزی پیدا نکرد» با «نگهبان اجرا نشد» یکی نیست. امروز این دو قابل تفکیک نیستند و همین باعث می‌شود نشود ثابت کرد نگهبان واقعاً روی همهٔ مسیرها رفته.

**۲. `rewrite` در کنار `block`.** تسویه رویداد را رد نمی‌کند؛ ماهیتش را عوض می‌کند. اگر تنها گزینه‌ها «عبور» و «رد» باشند، نگهبان تسویه مجبور می‌شود رویداد درست را به صف بفرستد.

**۳. دلیل اجباری است.** پرامپت می‌گوید رد نگهبان باید با دلیل خوانا به صف برود و هیچ‌وقت بی‌صدا دور ریخته نشود.

### جای اجرا

نگهبان‌ها **پیش از** موتور قاعده و **پس از** موتور تصمیم اجرا می‌شوند:

```
رویداد → تصمیم (ماهیت چیست) → نگهبان‌ها (آیا اصلاً باید ثبت شود) → قاعده → سند
```

دلیل این ترتیب: نگهبان تسویه باید بداند رویداد چه ماهیتی دارد تا بفهمد آیا «درآمد یا هزینهٔ تازه» است که باید جلویش را بگیرد. نگهبانی که پیش از تصمیم اجرا شود، این را نمی‌داند.

## دلتای کارت طرف حساب

کارت امروز فقط می‌خواند. برای نگهبان تسویه باید بتواند «اسناد باز این شخص» را با مبلغ برگرداند:

```js
openDocumentsFor(contactId) => [
  { kind: 'invoice' | 'obligation' | 'cheque', id, direction, amount, remaining, reference, occurredAt }
]
```

منبعش همان جدول‌های موجود است (`obligations`، `invoices`، `cheques`) که `documentBalance` امروز جمعشان را حساب می‌کند؛ کار تازه فقط برگرداندن ردیف‌ها به‌جای جمع است.
