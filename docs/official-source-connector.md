# اتصال به منابع رسمی سازمان امور مالیاتی — پیشنهاد طراحی

**وضعیت: پیشنهاد. هیچ کدی پیاده‌سازی نشده است.** این سند مکمل [ماژول هوش مالیاتی](tax-intelligence-module.md) است و فقط به یک پرسش پاسخ می‌دهد: چطور حساب‌یار به آنچه سازمان امور مالیاتی منتشر می‌کند وصل شود، به‌طوری‌که هر پاسخ نرم‌افزار به همان منبع رسمی استناد کند.

---

## ۱. سه اتصال متفاوت که یکی نیستند

«وصل‌شدن به tax.gov.ir» در عمل سه پروژهٔ جداست با سه نوع دشواری. قاطی‌کردنشان بزرگ‌ترین ریسک این کار است:

| | چه چیزی | جهت داده | مانع اصلی |
| --- | --- | --- | --- |
| **الف** | قانون، آیین‌نامه، بخشنامه، دستورالعمل، آرا | خواندن | API عمومی مستندی وجود ندارد؛ باید از صفحات رسمی برداشت شود |
| **ب** | سامانهٔ مؤدیان: ارسال صورتحساب الکترونیکی، کارپوشه | نوشتن و خواندن | مانع فنی نیست، **مانع حقوقی و هویتی** است: گواهی امضای الکترونیکی، شناسهٔ یکتای حافظهٔ مالیاتی، و احتمالاً جایگاه شرکت معتمد |
| **ج** | استعلام‌ها (اعتبار مؤدی، شمارهٔ اقتصادی) | خواندن | دسترسی سازمانی و توافق‌نامه لازم دارد |

آنچه تو خواستی — «هر اطلاعاتی آنجا قرار می‌گیرد، نرم‌افزار به آن استناد کند» — دقیقاً **الف** است. این سند عمدتاً دربارهٔ الف است؛ ب و ج در بخش ۷ با پیش‌نیازهایشان می‌آیند تا با الف اشتباه گرفته نشوند.

> **محدودیت این بررسی:** در محیطی که این سند نوشته شده، خروجی شبکه به `tax.gov.ir` و `intamedia.ir` بسته است و نتوانستم ساختار واقعی صفحات، وجود RSS یا نیاز به جاوااسکریپت را ببینم. پس معماری زیر عمداً **آگنوستیک نسبت به شکل منبع** طراحی شده و اولین کار اجرایی‌اش یک «کاوش قابلیت» است که باید توسط کسی با دسترسی شبکه انجام شود (بخش ۳).

---

## ۲. اصل حاکم: اتصال، منبع را معتبر نمی‌کند

وسوسه این است که چون داده مستقیم از سایت سازمان می‌آید، خودکار منتشر شود. این اشتباه است و همان قاعده‌ای را می‌شکند که کل ماژول رویش ساخته شده:

- صفحهٔ فهرست، **خبر** و **بخشنامه** را کنار هم می‌گذارد. برداشت خودکار بدون طبقه‌بندی، خبر را به قانون تبدیل می‌کند.
- یک صفحه ممکن است پیش‌نویس، اطلاعیه یا «به‌زودی» باشد.
- تغییر قالب سایت، بی‌صدا داده را خراب می‌کند و کسی متوجه نمی‌شود مگر اینکه سیستم خودش شک کند.

پس: **اتصال خودکار فقط تا صف بازبینی پیش می‌رود.** انتشار، امضای انسانی می‌خواهد — همان `verified_by` که در مدل دادهٔ سند اصلی تعریف شد و همان قاعده‌ای که امروز هم در `saveTaxKnowledgeSource` هست.

تنها استثنا برای شتاب کار: سندی که **دقیقاً همان سند قبلی با تغییر جزئی** باشد (تغییر `content_hash` بدون تغییر شماره و تاریخ‌ها) می‌تواند به‌صورت «نسخهٔ کاندید» ثبت شود و در رابط با نشان تغییر بیاید — ولی تا تأیید، نسخهٔ فعال عوض نمی‌شود.

## ۳. گام صفر: کاوش قابلیت منبع

پیش از نوشتن هر آداپتوری، برای هر دامنهٔ رسمی یک برگهٔ کاوش پر می‌شود. بدون این برگه، آداپتور نوشته نمی‌شود:

```yaml
domain: intamedia.ir
purpose: بخشنامه و دستورالعمل سازمان امور مالیاتی
robots_txt: <متن، تاریخ بررسی>
terms_of_use: <پیوند و خلاصه؛ آیا برداشت خودکار منع شده؟>
feeds: [rss?, atom?, sitemap.xml?]        # ارزان‌ترین مسیر، اگر باشد
listing_url_pattern: ...
pagination: query-param | path | infinite-scroll
rendering: static-html | requires-js
fields_available: [شماره, تاریخ صدور, تاریخ اجرا, موضوع, فایل پیوست]
attachment_types: [pdf, jpg-scan, docx]
scan_only: true|false                     # اگر تصویری است، OCR لازم است
rate_limit_observed: ...
sample_documents: [3 نمونهٔ واقعی برای آزمون آداپتور]
```

ترتیب اولویت مسیرها همیشه یکی است و از ارزان به گران می‌رود: **feed رسمی ← sitemap ← صفحهٔ فهرست ساده ← رندر با مرورگر**. آخری پرهزینه، شکننده و آخرین گزینه است.

**دروازهٔ حقوقی.** اگر شرایط استفادهٔ دامنه برداشت خودکار را منع کند یا مبهم باشد، آداپتور نوشته نمی‌شود تا وقتی پاسخ مکتوب گرفته شود. محصولی که خودش را «منبع‌دار» می‌نامد نمی‌تواند منبعش را بی‌اجازه بردارد.

## ۴. معماری آداپتور

هر منبع رسمی یک آداپتور با قرارداد ثابت است. هستهٔ سیستم هیچ چیزی دربارهٔ HTML یک سایت خاص نمی‌داند:

```js
// server/sources/adapters/<name>.js
export const adapter = {
  id: 'inta-circulars',
  domain: 'intamedia.ir',
  documentClass: 'circular',        // پیش‌فرضِ پیشنهادی، نه قطعی
  authorityTier: 4,

  // ① فهرست: چه چیزهایی هست؟ فقط فراداده، بدون دانلود متن کامل
  async discover({ since, page }) → [{ externalId, title, publishedAt, url, hints }],

  // ② دریافت یک سند
  async fetchDocument({ url }) → { html|pdf|image, headers, fetchedAt },

  // ③ استخراج فراداده و متن، با اطمینان اعلام‌شده
  extract(raw) → {
    officialNumber, approvedAt, effectiveFrom, title, bodyText,
    confidence: { officialNumber: 0..1, approvedAt: 0..1, ... },
    warnings: ['تاریخ اجرا در متن پیدا نشد'],
  },

  // ④ سلامت: آیا قالب سایت عوض شده؟
  selfCheck() → { ok, changedSelectors: [...] },
};
```

چهار تصمیم پشت این قرارداد:

**۱. `discover` از `fetch` جداست.** فهرست‌خوانی ارزان و مکرر است؛ دانلود متن گران و کم‌تکرار. جداکردنشان یعنی می‌شود روزی چند بار فهرست را دید بدون اینکه باری روی سایت رسمی گذاشته شود.

**۲. استخراج، اطمینان اعلام می‌کند.** فیلدی که با اطمینان پایین استخراج شده، در صف بازبینی **برجسته** می‌شود. این همان الگویی است که در `confidenceDetails` تراکنش‌ها از قبل کار می‌کند.

**۳. `selfCheck` اجباری است.** آداپتور باید بتواند بگوید «ساختاری که انتظار داشتم دیگر نیست». تغییر قالب سایت رسمی حتمی است؛ سیستمی که آن را نفهمد، بی‌صدا داده‌های ناقص تولید می‌کند. شکست `selfCheck` یک هشدار عملیاتی می‌سازد، نه یک ورود خاموش.

**۴. سند تصویری، پرچم می‌گیرد.** بخشنامهٔ اسکن‌شده باید OCR شود و OCR خطا دارد. چنین سندی هرگز بدون بازبینی متن منتشر نمی‌شود و در پاسخ‌ها برچسب «متن از تصویر استخراج شده» می‌گیرد.

## ۵. چرخهٔ اجرا

```
زمان‌بند (روزانه/ساعتی، با احترام به rate limit)
   │
   ├─ discover(since=آخرین اجرای موفق)
   │     └─ سند تازه؟ → صف دریافت
   │
   ├─ fetch + extract
   │     ├─ content_hash تازه؟
   │     │      ├─ سند کاملاً نو  → نسخهٔ ۱، وضعیت pending-review
   │     │      └─ سند موجود تغییر کرده → نسخهٔ کاندید، نسخهٔ فعال دست‌نخورده
   │     └─ تکراری → فقط last_seen_at به‌روز می‌شود
   │
   ├─ طبقه‌بندی پیشنهادی (کلاس سند، ردیف اقتدار، روابط اصلاح/نسخ/ابطال)
   │
   ▼
صف بازبینی انسانی ──تأیید──▶ انتشار نسخه ──▶ نمایه‌سازی ──▶ قابل استناد
        │
        └──رد──▶ بایگانی با دلیل (برای اینکه دفعهٔ بعد دوباره پیشنهاد نشود)
```

**ثبت اجرا.** هر اجرا یک ردیف در `ingestion_runs` می‌سازد: چند سند دیده شد، چند تازه بود، چند خطا، و **دلیل هر خطا**. اجرایی که هیچ سندی پیدا نکند در حالی که قبلاً می‌کرد، خودش یک هشدار است — احتمالاً سایت عوض شده، نه اینکه بخشنامه‌ای صادر نشده.

**نسخهٔ محلی همیشه می‌ماند.** فایل خام (HTML/PDF) با hash خودش ذخیره می‌شود. اگر سایت رسمی صفحه‌ای را بردارد — که می‌افتد — استناد قدیمی نباید به ۴۰۴ ختم شود. در رابط، هم پیوند رسمی و هم «نسخهٔ بایگانی‌شده در تاریخ فلان» نشان داده می‌شود.

**احترام به سایت رسمی.** تک‌جریانه، با فاصله میان درخواست‌ها، `If-Modified-Since`، و توقف خودکار روی ۴۲۹/۵xx با عقب‌نشینی نمایی. سازمان امور مالیاتی زیرساخت ما نیست.

## ۶. استناد: اینکه «نرم‌افزار به آن استناد کند» یعنی چه

استناد در این طراحی یک رشتهٔ متنی نیست، یک **پیوند داده‌ای** است. هر پاسخ، فرصت یا کسر نمره به `provision_id` وصل می‌شود و از آنجا:

```
پاسخ ──▶ ماده/بند ──▶ نسخهٔ سند ──▶ سند
                          │
                          ├─ شمارهٔ رسمی، مرجع صادرکننده
                          ├─ تاریخ تصویب / اجرا / پایان اعتبار
                          ├─ پیوند رسمی + نسخهٔ بایگانی‌شده
                          ├─ تأییدکنندهٔ انسانی و تاریخ تأیید
                          └─ روابط: اصلاح‌شده با…، ابطال‌شده با…
```

سه رفتار که از این پیوند بیرون می‌آید و در نسخهٔ رشته‌ای ممکن نیست:

1. **هشدار کهنگی.** وقتی سندی که پاسخ قبلی به آن استناد کرده اصلاح یا ابطال شود، همهٔ پاسخ‌های ذخیره‌شدهٔ متکی به آن نشان «مبنای این پاسخ تغییر کرده» می‌گیرند. پاسخ قدیمی بازنویسی نمی‌شود — سابقه است — ولی کاربر می‌فهمد.
2. **پاسخ سال‌آگاه.** همان پرسش برای ۱۴۰۳ و ۱۴۰۵ به دو نسخهٔ متفاوت استناد می‌کند، چون بازیابی با سال مالی مورد سؤال فیلتر می‌شود، نه با امروز.
3. **پوشش قابل سنجش.** می‌شود گفت «پایگاه ما تا تاریخ فلان از این منبع کامل است»؛ چیزی که با برداشت دستی هرگز قابل ادعا نیست.

## ۷. سامانهٔ مؤدیان — چرا پروژهٔ جداست

اگر منظورت از «وصل‌شدن» ارسال صورتحساب به سامانهٔ مؤدیان هم هست، این مسیر **فنی نیست، حقوقی است** و پیش‌نیازهایش قبل از هر خط کد باید تأمین شوند:

- **هویت مؤدی**: ثبت‌نام در کارپوشه و دریافت شناسهٔ یکتای حافظهٔ مالیاتی.
- **گواهی امضای الکترونیکی** از مراکز میانی مورد تأیید؛ کلید خصوصی باید در سمت مؤدی بماند.
- **جایگاه حقوقی حساب‌یار**: نرم‌افزاری که به‌جای مشتری صورتحساب می‌فرستد، وارد نقش «شرکت معتمد ارائه‌کنندهٔ خدمات مالیاتی» می‌شود که خودش مجوز و الزامات دارد. جایگزین سبک‌تر: حساب‌یار **فایل/بستهٔ آمادهٔ ارسال** بسازد و ارسال با خود مؤدی یا معتمد او باشد — دقیقاً همان الگویی که امروز برای پل پارسیان انتخاب شده و جواب داده.
- **الزامات ساختاری صورتحساب**: شناسهٔ کالا/خدمت، شمارهٔ اقتصادی خریدار، الگوی صورتحساب، شمارهٔ منحصربه‌فرد مالیاتی، و قواعد اصلاح/ابطال. هیچ‌کدام امروز در حساب‌یار نیست و [`docs/tax-and-vat.md`](tax-and-vat.md) صریحاً همین را به‌عنوان محدودیت نسخه اعلام کرده.
- **مشخصات فنی** (نشانی سرویس، قالب پیام، امضا و رمزنگاری) باید از **آخرین دستورالعمل رسمی همان زمان** برداشته شود، نه از حافظه و نه از مقالهٔ آموزشی. هر عددی که من اینجا بنویسم ممکن است تا زمان اجرا کهنه شده باشد.

**پیشنهاد من:** مسیر الف (منابع قانونی) را حالا بسازیم، مسیر ب را با گزینهٔ «بستهٔ آمادهٔ ارسال» شروع کنیم و ارسال مستقیم را فقط با تصمیم حقوقی روشن و شریک معتمد باز کنیم. مسیر ج (استعلام) تا وقتی دسترسی سازمانی نداریم، اصلاً شروع نشود.

## ۸. امنیت و مرزها

- **پایگاه اسناد قانونی، دادهٔ مشتری نیست**: مشترک، فقط‌خواندنی برای دفترها، و نوشتن در آن فقط از مسیر ممیزی‌شدهٔ مدیر سامانه.
- **متن دریافتی، دادهٔ نامعتمد است.** سندی که از اینترنت آمده در قالب مرزبندی‌شده به مدل داده می‌شود؛ هر «دستور» داخلش بخشی از متن است، نه فرمان.
- **هیچ داده‌ای از دفتر به بیرون نمی‌رود** در این مسیر. اتصال یک‌طرفه است: از سایت رسمی به ما.
- **سهمیه و هزینه** از همان `provider_usage` موجود عبور می‌کند؛ OCR و embedding انبوه نباید سهمیهٔ صدای مشتری را بخورد.
- **کلیدها و گواهی‌ها** (اگر روزی مسیر ب باز شود) هرگز در مخزن یا در دیتابیس دفتر نمی‌نشینند.

## ۹. فازبندی

| فاز | محتوا | معیار پذیرش |
| --- | --- | --- |
| **۰** | برگهٔ کاوش قابلیت برای دامنه‌های رسمی + پاسخ مکتوب حقوقی | بدون این، فاز ۱ شروع نمی‌شود |
| **۱** | قرارداد آداپتور + آداپتور اول (کم‌ریسک‌ترین منبع با ساختارمندترین صفحه) | ۳ سند نمونه با فراداده کامل استخراج شوند؛ `selfCheck` روی قالب تغییریافته شکست بخورد |
| **۲** | زمان‌بند، `ingestion_runs`، تشخیص تغییر با hash، بایگانی نسخهٔ خام | اجرای بی‌نتیجه هشدار بسازد؛ استناد به صفحهٔ حذف‌شده به نسخهٔ بایگانی برسد |
| **۳** | صف بازبینی با برجسته‌سازی فیلد کم‌اطمینان و طبقه‌بندی پیشنهادی | هیچ سندی بدون تأیید انسانی منتشر نشود |
| **۴** | پیوند استناد + هشدار کهنگی روی پاسخ‌های قدیمی | اصلاح یک سند، همهٔ پاسخ‌های متکی به آن را نشان‌دار کند |
| **۵** | آداپتور دوم و سوم (بخشنامه، آرا) + OCR اسناد تصویری | سند تصویری برچسب OCR بگیرد و بدون بازبینی متن منتشر نشود |
| **۶** | گزارش پوشش: «از این منبع تا این تاریخ کامل‌ایم» | عدد پوشش از `ingestion_runs` ساخته شود، نه از ادعا |

مسیر ب (مؤدیان) فازبندی جداگانه و پیش‌نیاز حقوقی دارد و در این جدول عمداً نیامده.

## ۱۰. آنچه این اتصال تضمین نمی‌کند

- کامل‌بودن پایگاه نسبت به همهٔ آنچه منتشر شده؛ فقط پوشش منابع پیکربندی‌شده گزارش می‌شود.
- درستی تفسیر؛ اتصال متن را می‌آورد، معنا را متخصص تأیید می‌کند.
- به‌روزبودن لحظه‌ای؛ فاصلهٔ میان انتشار رسمی و تأیید انسانی در رابط نمایش داده می‌شود.
- جایگزینی مراجعهٔ رسمی؛ هیچ اظهارنامه، صورتحساب یا اعتراضی از این مسیر ارسال نمی‌شود.
